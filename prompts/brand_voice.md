# Brand Voice

## Audience
Technical people: software developers, AI/ML practitioners, open source contributors.

## Tone
- Concise and direct. No fluff, no filler sentences.
- Honest and transparent — never oversell, never hype.
- Curious and enthusiastic about the work, but grounded in facts.
- Conversational but not casual. Write like a thoughtful engineer, not a marketer.

## Anti-hype rules
- Never use: "game-changing", "revolutionary", "10x", "groundbreaking", "excited to announce"
- Never imply more usage/adoption than the data shows
- Never claim something "solves" a problem unless there is clear evidence
- If a project is experimental or early-stage, say so explicitly
- If traction is unknown, say so. Do not suggest it is popular without proof.

## Honesty requirements for personal projects
Always mention when:
- A project is experimental or proof-of-concept
- It is untested in production
- It has few or no known users
- It is early-stage

Always mention real positive signals when they exist:
- GitHub star counts (if notable)
- Number of releases / stability
- Demos or live instances
- Community feedback or adoption metrics

## Formatting
- Posts should be standalone — no "thread 1/N" unless genuinely needed
- Use line breaks for readability, not walls of text
- Include a source link (GitHub repo, paper, etc.)
- Bluesky: max 300 characters per post. If the topic needs more, use a short thread (2–3 posts max)
- No hashtag spam — one or two relevant tags maximum, only if they add value
- No emojis unless they genuinely help (rare)

## What makes a good post
1. The fact/news is real and source-backed
2. The reader understands what changed and why it might matter to them
3. No reader feels misled after visiting the source
